## 1. Analysis

views are allowed, how repeated actions are counted, which flags exist. Segments (W3, P8.06), references (P6), the
comparison rules (P6.05) and the pilot reports all use these labels, so a typo here would silently split data.

**Design:**

```yaml
schema_version: ontology/1
ontology_version: v0
form:
  id: taiji24
  name_en: ...           # variant name, confirmed by H
  expected_actions: 24
  status: draft_unconfirmed      # confirmed needs confirmed_by (role) and confirmed_at (date)
sides: [left, right, none]
view_categories: [front, side, oblique, back, unknown]
flags: [orientation_change, occlusion, perspective_shift]
actions:
  - id: A01                  # one numbered movement of the form
    slug: commencement
    technique: commencement  # shared key when the same technique has two numbers
    name_en: ...
    name_zh: ...
    name_vi: ...
    sides: [none]            # the sides that occur inside this movement
    repetitions: 1           # how often it is performed inside the movement; H confirms
```

An **action is one numbered movement of the form**, so the 24-form has 24 actions. In the commonly taught version some
movements alternate sides inside one number (repeated left and right), while others exist as two numbers, one per side,
and one technique can appear under two numbers; H confirms all of this for the chosen variant. Therefore `sides` lists
the sides that occur inside a movement (a movement numbered per side has one side), `repetitions` is the expected count
inside it, and a segment's `occurrence` is the repetition index from 1 to `repetitions`. `technique` groups numbers
that are the same technique, so that P6 can later decide whether a reference may come from the other number.

The validator: unique `id` and `slug`; every `sides` value in the declared `sides`; `repetitions` at least 1;
`expected_actions` equals the count; `confirmed` implies `confirmed_by` and `confirmed_at`; unknown keys rejected;
`schema_version` must equal `ontology/1`. `Ontology.check_segment(action, side, view_category, flags, occurrence)`
raises an `OntologyError` (a `ValueError`) that lists the valid values.

- **Plan changes found at the re-read (before any code):**
  1. YAML `safe_load` silently keeps the last value of a duplicated key, so a repeated `slug:` would pass: the loader is a
     `SafeLoader` subclass that rejects duplicate keys. New test group **T-DATA-01h**: unsafe tag, duplicate key, invalid
     YAML, top level not a mapping, all giving `OntologyError`.
  2. `parse_ontology(data)` and `load_ontology(path)` both raise `OntologyError` (YAML errors and Pydantic errors are
     wrapped), so callers catch one type.
  3. `check_segment`: `side=None` means `"none"` (the database column is nullable); `occurrence=None` means the whole
     movement and is accepted; an integer must be in 1..`repetitions`; flag values must be booleans (the database stores
     a JSON object).
  4. A `draft_unconfirmed` form must not carry `confirmed_by` or `confirmed_at` (an inconsistent record would mislead).
- Dependency: `pyyaml` added with `py -3.12 -m uv add pyyaml` after the tests are written red.
