## 1. Analysis

**Why this task:** ingest (P2.02) must refuse a recording unless its participant exists with a consent reference and
analysis consent (AGENTS.md §9.5). No task in the plan writes a `participant` row: P9.01 is O's recruiting and consent step
(its check T-DATA-02 says every recording has a participant with valid consent), and P8 has no participant page. Without
this task the first real ingest (P2.07) has nothing to link to, and the rows would be written by hand in SQL, with no check
and no audit.

**Facts read (2026-11-15):** `participant` (`participant_id` PK, `level_self`, `level_coach`, `consent_ref` NOT NULL,
`consent_analysis` default 1, `consent_train` default 0, `consent_share` default 0, `retention_until`, `created_at`);
`audit_log` (`actor`, `action`, `entity`, `before`, `after`, `at`); the consent form's mapping (P1.06 B1): box (a) → 1 or no
participant at all, boxes (b) and (c) → 1 or 0, retention as an ISO date; the database itself accepts `consent_analysis = 0`,
so the code must refuse it; minor status and the form version are kept in O's register, not in the database.

**In scope:** `store/participants.py`: `register_participant(conn, participant_id, consent_ref, analysis, train, share,
retention_until, actor)`, `update_consent(conn, participant_id, train=…, share=…, retention_until=…, actor)`,
`get_participant(conn, participant_id)`; every write adds an `audit_log` row (`before` and `after` as JSON of the consent
fields; IDs only); CLI `taiji participant add | set | show`.

**Out of scope:** withdrawal and deletion (P8.14), a UI page (P8), O's register with real names (never in the system).

**Design rules:** `participant_id` and `consent_ref` follow the P2.01 patterns; `analysis` must be true (else refused with a
message that points to the consent form); `train` and `share` must be given explicitly (no silent default for a consent
question); `retention_until` is an ISO date or empty with a warning; `level_self` and `level_coach` are not set here (they are
not consent data).

## 3. Plan re-read (before coding)

- Plan re-read: 2026-11-16 — OK against the current files: `participant` and `audit_log` are as described in migration 0001
  (`consent_analysis` is `CHECK IN (0, 1)` with default 1, so the database cannot refuse a missing answer); `store/db.connect`
  applies the migrations and sets `foreign_keys = ON`; there is no `cli.py` and no `[project.scripts]` yet (so this task
  creates both and P2.02 only adds its commands); `configure_logging` is for entry points only, the tests use the
  `clean_logging` fixture (`conftest.py`) for anything that calls it; P2.01 gives the ID patterns (`PARTICIPANT_RE`,
  `CONSENT_RE` in `schemas/_base.py`).
- **Additions found at the re-read (the plan's steps stay):**
  1. All consent answers are **keyword-only and have no default** in `register_participant` (`analysis`, `train`, `share`),
     so a call cannot pass the three booleans in the wrong order or forget one; a non-boolean (`1`, `"yes"`, `None`) is
     refused, not read as true. The CLI flags `--analysis`, `--train`, `--share` are required and take `yes` or `no`.
  2. `retention_until` must be a real ISO date (`YYYY-MM-DD`) and not in the past (a past date would mean "delete at once",
     almost certainly a typo); none is allowed, with a logged warning. `today` can be injected for tests.
  3. `actor` must be a role code `cli:A`, `cli:B`, `cli:O` or `cli:H` with up to two digits (for example `cli:H1`), which the
     plan names (A, B, O, H); a person's name does not fit the pattern.
  4. `update_consent` cannot change `analysis` (withdrawing it is a deletion, P8.14) or `consent_ref`; it changes only the
     fields that are given; nothing given is an error; giving the current values is a no-op without an audit row.
  5. Every write is one transaction with its audit row: a failure of the audit insert leaves no participant row.
  6. The CLI writes results to standard output, errors to standard error, exit code 0 ok, 1 refused, 2 usage (argparse); no
     path and no free text is logged or echoed, only IDs.
  7. Tests: T-DATA-05a..e of the plan plus T-DATA-05f..j (dates, actors, atomicity, no-op update, the command line).
