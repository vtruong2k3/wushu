## 1. Analysis

**Why this task:** ingest (P2.02) must refuse a recording unless its participant exists with a consent reference and
analysis consent (AGENTS.md §9.5). No task in the plan writes a `participant` row: P9.01 is O's recruiting and consent step
(its check T-DATA-02 says every recording has a participant with valid consent), and P8 has no participant page. Without
this task the first real ingest (P2.07) has nothing to link to, and the rows would be written by hand in SQL, with no check
and no audit.

**Facts read (2026-11-15):** `participant` (`participant_id` PK, `level_self`, `level_coach`, `consent_ref` NOT NULL,
`consent_analysis` default 1, `consent_train` default 0, `consent_share` default 0, `retention_until`, `created_at`);
`audit_log` (`actor`, `action`, `entity`, `before`, `after`, `at`); the consent form's mapping (P1.06 B1): box (a) → 1 or no
participant at all, boxes (b) and (c) → 1 or 0, retention as an ISO date; the database itself accepts `consent_analysis = 0`,
so the code must refuse it; minor status and the form version are kept in O's register, not in the database.

**In scope:** `store/participants.py`: `register_participant(conn, participant_id, consent_ref, analysis, train, share,
retention_until, actor)`, `update_consent(conn, participant_id, train=…, share=…, retention_until=…, actor)`,
`get_participant(conn, participant_id)`; every write adds an `audit_log` row (`before` and `after` as JSON of the consent
fields; IDs only); CLI `taiji participant add | set | show`.

**Out of scope:** withdrawal and deletion (P8.14), a UI page (P8), O's register with real names (never in the system).

**Design rules:** `participant_id` and `consent_ref` follow the P2.01 patterns; `analysis` must be true (else refused with a
message that points to the consent form); `train` and `share` must be given explicitly (no silent default for a consent
question); `retention_until` is an ISO date or empty with a warning; `level_self` and `level_coach` are not set here (they are
not consent data).
