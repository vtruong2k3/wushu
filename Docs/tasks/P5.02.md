## 1. Analysis

**Goal.** P5.03 (hip height A), P5.04 (B), P5.05 (trunk lean), P5.06 (speed) and P6.01 (normalised features) all start from the same four things of Appendix B:
the mid-hip `H(t) = (p11 + p12) / 2`, the mid-shoulder `S(t) = (p5 + p6) / 2`, the trunk length `L(t) = |S(t) - H(t)|` and its scale `Λ = median_t L(t)` over the valid
frames, plus the camera roll that has to be taken out of a vertical coordinate or an angle (`roll_cam` from a vertical line the user draws on a reference frame,
default 0). P5.02 writes them once, with the conventions fixed and tested, so that no metric re-derives a midpoint or invents its own scale. No metric is computed here.

**Source rules read.** Plan row P5.02 and tests T-MET-01 (mid-hip, mid-shoulder, Λ = median, NaN ignored) and T-MET-02 (SYN-04: the roll is corrected right); W7 and Appendix B of
`Docs/TECH_WORKFLOW_V1.md` (pixels of the image, y down; `Λ` is the median of `L(t)` on the valid frames; `θ(t) = atan2(x_S - x_H, y_H - y_S) - roll_cam`, 0° vertical, positive to
the image right; `roll_cam` from a user-drawn vertical line, default 0); v3 section 6.1 ("after a valid camera roll correction"); SYN-03 and SYN-04 of the generator (`tests/helpers/synth.py`:
`vertical_line` = two image points (top, bottom) of a line that is truly vertical, rotated by β with the same sign as θ; `theta_raw_deg = θ_body + β`; tolerance 0.5° median error at
noise ≤ 1 px and scale 200 px); DEC-0014 (hip variants A and B); P5.01 (`MissingReason` codes 1 to 6 are the quality reasons, a metric row with no value must have a reason, "the reason of the first
unusable required joint, in the order of the metric" is stated by each metric task); P6.01 (the same midpoint and Λ per segment). Existing code read: `quality/filters.py` (`torso_length_px`, `TORSO_JOINTS`),
`quality/_checks.py` (`check_gap_layer`: the contract of the final layer), `pose/skeleton.py`, `quality/layers_io.py` (`PoseFiltered`), `schemas/metric.py`, `metrics/series.py`.

**Two facts that shape the plan.**

1. **`quality.filters.torso_length_px` already holds the definition of Λ, on the mask layer** (median over the frames in which the four torso joints are `ok`; a distance of 0 is left out). The
   metrics read the **final layer**, where a short gap is bridged: a bridged cell has a value, a reason that is not `ok` and the flag `interpolated`, so that function (which checks "finite exactly where `ok`")
   cannot take it. P5.02 gives the metrics their own function on the final layer and **a test that the two agree** on a layer with no bridged cell, so there is one definition and two doors.
2. **A bridged cell is a flagged value, not a missing one.** AGENTS.md 5.1 allows it when it is flagged; the final layer carries the flag. Default (Q1): a joint is *usable* when its value is finite
   (observed or bridged); a joint that is not carries the reason that the layer gives it (1 to 6); and the functions can say which rows lean on a bridged value, so that a metric can count them and a
   report can show them. Nothing is hidden and nothing is filled.

**In scope.** `metrics/geometry.py` with:

| Function | What it gives |
|---|---|
| `midpoint(keypoints, joints)` | `(N, 2)` float64: the mean of the given joints of every row; NaN where any of them is NaN. `mid_hip` and `mid_shoulder` are the two uses (joints 11, 12 and 5, 6; **not** the model's own `Hip` (19) and `Neck` (18), which Appendix B does not use) |
| `unusable_reason(keypoints, reason, joints)` | `(N,)` uint8: 0 when every joint of the list has a value; else the reason of the **first joint of the list** that has none (1 to 6): the rule that P5.01 left to the metric tasks, stated once |
| `bridged(interpolated, keypoints, joints)` | `(N,)` bool: a joint of the list has a value that is a bridge (flag `interpolated`) |
| `trunk_length(keypoints)` | `(N,)` float64: `L(t) = \|S - H\|`, NaN where a midpoint is NaN; a distance of exactly 0 (shoulders on the hips) is NaN too: it is not a trunk |
| `trunk_scale(length, rows=None)` | `TrunkScale(scale_px, n_rows)`: `Λ` = the median of `L` over the rows (a boolean mask; default all) where `L` is finite; `NaN` and 0 rows when none: the caller gives the rows `scale_unavailable` (the reason 19 of P5.01) |
| `roll_from_line(top, bottom)` | degrees: the roll of the camera from the two points of a user-drawn vertical line, `atan2(x_top - x_bottom, y_bottom - y_top)`, the same sign as θ; refused if the line is degenerate, horizontal-ish or more than 45° from vertical |
| `correct_roll(points, roll_deg, origin=(0, 0))` | the points in the frame where the reference line is vertical (rotation by `-roll`): x to the right, y down, as before; only differences of the result are meaningful (the origin is arbitrary) |
| `lean_angle_deg(mid_hip, mid_shoulder, roll_deg=0)` | `(N,)` degrees: `atan2(x_S - x_H, y_H - y_S) - roll`, wrapped to (-180, 180]; 0 is vertical, positive leans to the image right; NaN where a midpoint is NaN or the two coincide |

Plus T-MET-01 and T-MET-02 with their sub-IDs, the doc notes, a DEC and tracking.

**Out of scope.** Any metric or statistic (P5.03 to P5.07); the view conditions and flags of the interval (P5.05, and the reasons 16 to 18 that P7 passes); the slicing of the segment rows out of a
`PoseFiltered` (`grid_in_segment`, the step, the reason and flag arrays): the first metric that needs it, P5.03, writes that few lines and the others reuse them; the choice of the reference standing segment for
variant A (P5.03; here `trunk_scale` only takes the rows it is given); per-frame Λ (DEC-0014: not added); any threshold or limit on a metric; reading or writing files.

**Conventions fixed by this task** (each is a place where two metrics could otherwise disagree):

1. **Pixels of the upright image, x right, y down**; computed in float64 whatever the input dtype; arrays returned are new and read-only; inputs are never changed.
2. **The sign of an angle** is that of Appendix B2 and of the generator: `atan2(Δx, -Δy)` of the vector hip to shoulder, positive when the top leans to the image right; the roll has the same sign
   (`roll_from_line`), so `θ_corrected = θ_raw - roll` is a subtraction of two angles of one convention and `correct_roll` is its coordinate form: with `u = (sin roll, -cos roll)` the corrected "up" and
   `r = (cos roll, sin roll)` the corrected "right", `x' = (p - o) . r`, `y' = (p - o) . (-u)`. (Checked below against the generator's own `apply_roll`, which is independent code.)
3. **Usable = a finite value**, observed or bridged (Q1); a row whose list of joints has a joint with no value takes the reason of the **first such joint in the order of the list**; bridged rows are reported
   by `bridged`, not hidden and not forbidden.
4. **Λ is the median of `L(t)` over the valid rows**, valid = both midpoints finite and `L > 0`; the rows are the caller's (the segment, or the reference standing segment of variant A, or the segment of
   a comparison in W8); no minimum count here (a `metric_record` will carry the minimum valid duration): the function returns `n_rows` and the metric decides.
5. **The roll limit is 45°** (the generator's own limit): more is a rotated video, which the display rotation of ingest handles, not a camera roll to correct. It is a validity limit of an input, not a
   threshold on a movement (AGENTS.md 5.5).

**Existing code and docs read** (paths): as listed above. **Constraints that apply (AGENTS.md section 5):** 1 no fabricated observation (a NaN stays NaN with a reason; a degenerate trunk is NaN, not 0 and not
a guessed angle); 2 real timestamps (these functions do not look at time); 4 units and coordinates documented in each docstring; 5 no threshold; 11 no third-party code.

**Unknowns, risks, questions** (answered with the defaults below so that P5.03 can follow; each can be reversed before P5.03 uses it):

- **Q1. Do bridged cells count as usable?** Default **yes, flagged**: `bridged()` says which rows lean on one and a metric can count them (a statistic, or a parameter in its summary). Alternative: a metric
  refuses a bridged cell, which needs a new reason in the vocabulary of P5.01 (a version bump) and throws away short gaps that W6 chose to bridge.
- **Q2. Do `lean_angle_deg` and `correct_roll` belong here or in P5.05?** Default **here** as pure arithmetic: T-MET-02 ("SYN-04: the roll is corrected right") is listed for P5.02 and needs the angle; P5.05 adds the
  view condition, the statistics (median, P95 of `|θ|`) and the series.
- **Q3. The 45° limit and the refusal of a horizontal-ish line.** Default as in the generator. Alternative: accept any line and let a nonsense roll through (a hip-height range would then be rotated for nothing).
- **Q4. The origin of `correct_roll`.** Default `(0, 0)` and "only differences are meaningful": the ranges of Appendix B (`P95 - P5`, `g - y_H`) do not depend on it. Alternative: the image centre, which needs the image
  size at every call.
- **Q5. The glue from a `PoseFiltered` to the arrays** is left to P5.03 (see out of scope). Alternative: put it here as `segment_arrays(layer)`; it is about fifteen lines and would give P5.02 a fourth test group.
- **Q6. A trunk of length 0** is NaN, and the metric task gives such a row (all joints usable, no value) the reason `frame_invalid` (4: the frame cannot be used), so no new code is needed. It cannot happen on real
  pose output; it is the case of a hand-made or synthetic degenerate pose.
- *Risk:* the cross-check against `torso_length_px` is the only link between the metric scale and the quality scale; if one is changed alone the test fails, which is the intent.
- *Risk:* the contract of the final layer is checked here only as far as each function reads it (a few local lines, not the private `check_gap_layer`): a full check of a layer stays with the quality package
  (`PoseFiltered` is checked when it is read).

## 2. Plan

**Design.**

1. `metrics/geometry.py`, one module of pure functions on arrays; the layer arguments are `keypoints (N, 26, 2)` float (pixels), `reason (N, 26)` uint8 and `interpolated (N, 26)` bool. Each function checks
   only what it reads, with a few local lines (no import of the private `quality/_checks.py`): `unusable_reason` needs a value or a reason of 1 to 6 for every cell (a NaN with reason `ok`, or with a code that is not a
   quality reason, or half a cell, is refused); `bridged` needs the flag only on cells that have a value. `midpoint`, `trunk_length` and `lean_angle_deg` need only values (NaN or finite; an infinity is refused).
   Errors are `MetricError` naming the argument (shape, dtype, joints out of range, a degenerate or too tilted line, NaN in a `roll_deg`).
2. `TrunkScale` is a frozen dataclass `(scale_px, n_rows)`; `scale_px` is `NaN` with `n_rows == 0` when there is no valid row.
3. `unusable_reason` walks the joints of the list in order: for each row the reason of the first joint without a value; `0` if none. The reasons are the layer's own codes (the contract guarantees that a NaN cell has one
   of 1 to 6), so nothing is mapped.
4. Roll: `roll_from_line` orders the two points by `y` (the top has the smaller `y`), then `atan2(Δx, Δy)` in degrees; `correct_roll` is the rotation above; both take and return float64.

## 6. Self-review

Read again after the last edit: `metrics/geometry.py` (whole file, 295 lines), the two test files, the diff of the docs. Checklist of AGENTS.md section 2 step 4:

- **Does it do exactly what the plan says, nothing missing, nothing extra?** Yes. The three deviations are listed in section 4; nothing is computed that the plan did not name, and no metric exists yet.
- **Edge cases:** empty input (N = 0 for every function), NaN in one joint (only its row), a single row, no valid row for Λ (`TrunkScale(nan, 0)`), coincident midpoints and a trunk of length 0 (NaN, not an angle and not a zero), a joint list that is empty, repeated, out of range or a string, a roll beyond 45 degrees or NaN, a level or one-point line, a wrapped angle of exactly -180 (reported as 180), VFR (SYN-07: the module never looks at time), a rotated video (the roll limit refuses it and says why). - **No fabricated data:** found one hole, `lean_angle_deg` turned an infinite midpoint into an angle of 90 degrees (**BUG-0075**, fixed here). Elsewhere: NaN stays NaN with its reason; a bridged cell is a flagged value and is reported by `bridged`, not hidden; no forward-fill and no zero-fill.
- **Errors raised, never swallowed:** no `except: pass`. The one `try/except (TypeError, ValueError)` (in `correct_roll`, turning a ragged or non-numeric `origin` into `MetricError`) re-raises as a specific error with the value.
- **Tests fail when the behaviour breaks:** 44 mutants caught, each by the test of its own rule; the new check of BUG-0075 was red before the fix (4 of 4).
- **No secrets, personal data or absolute paths** in the code, tests or docs of this task.
- **Docs, docstrings and status:** W7 note, plan rows with sub-IDs, README row, DEC-0055, CHANGELOG, TASK_STATUS. A pipe inside a code span broke the table row of DEC-0055 and of the task file (found by the editor's markdown check): written as `norm(S - H)` and `\|S - H\|`.

**Left as it is, on purpose:** (1) `unusable_reason` does not check that a finite cell with a reason that is not `ok` carries the flag `interpolated` (and `bridged` does not check the reason): each function checks what it reads, and the whole contract of a layer is checked when `PoseFiltered` is read (X.29); (2) `trunk_length` scans the keypoints for infinities three times (once per midpoint and once itself): a few hundred thousand floats per recording, not worth a private fast path; (3) a bridged cell that sits inside a trunk length counts in Λ (Q1: it is a flagged value); P5.03 decides whether to report the number of bridged rows in a summary.
