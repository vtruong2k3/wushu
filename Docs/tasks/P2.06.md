## 1. Analysis

**Goal:** turn the audio result and the flash check into one decision: may the two cameras of a take be combined in metrics,
or only shown side by side? Then store the result where P3, P5 and P8 read it.

**Facts read (2026-11-15):** plan row: residual ≤ 1 frame → combine; larger → side by side only; output
`sync.json.usable_for_metrics`; T-SYNC-05 (residual > 1 frame → `false`). `data/takes/<take_id>/sync.json` (§4.1); the `sync`
table (P2.01 Q4: a row only for `status = ok`).

**Rule (written once as a constant, enforced by the `SyncManifest` validator):** `usable_for_metrics = true` only when
`status = ok`, the flash validation exists for the start and the end, and the larger residual ≤ 1 frame of the slower camera.
Every other case is `false` with a reason: `no_audio`, `audio_not_found`, `start_only`, `flash_not_found`, `residual_too_large`.
An unknown residual is never treated as a small one.

**In scope:** `io/sync_rule.py` (or a function in `audio_sync.py`): `decide_usability(audio, validation) -> (bool, reason)`;
`pipeline/sync_take.py`: `sync_take(take_id, settings)` (find the two recordings of the take, run P2.04 and P2.05, decide,
write `sync.json` atomically, upsert the `sync` row when `status = ok`, all in that order); CLI `taiji sync <take_id>`.

**Out of scope:** how P5 uses two cameras (later), more than two cameras, a manual sync tool (P8).

**Questions for the maintainer:**

| #  | Question | Default if no answer |

| Q1 | Flash found only at the start: usable? | No (`flash_not_found` at the end): the drift is then checked at one point only |
| Q2 | Re-running sync on a take | Overwrites `sync.json` and the row (the result is recomputable); the old file is not kept |
