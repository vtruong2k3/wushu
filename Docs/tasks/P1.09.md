## 1. Analysis

### 1.1 Goal

Two real phone videos of one full 24-form take (camera A and camera B) recorded by protocol 1.0, with the capture sheet,
that (1) prove the protocol works and give the measured values of version 1.1, and (2) are the first real data of the
project's own kind for ingest and sync (P2.07), the pose rerun (X.27) and the first look at the metrics (P5.10). They are
the "F-TRIAL" data of the plan: local only, never in git.

### 1.2 Why the plan is revised (2026-11-17)

The first plan (2026-11-15, history in §1.9) was written before P2, P3, P4 and P5.01–P5.08 existed. Read again against the
code and the registers on 2026-11-17, five facts change what the trial day must do:

1. **The lamp may be too weak for the flash detector (BUG-0066, S2, PLANNED).** `io/flash.py` needs a step of the
   frame-mean luma of 15 levels; the BUG-0066 probe found a lamp lighting 10 % of a 640x360 frame only just found
   (step 16.4) and 5 % not found. A lamp held at the chest at 4–5 m can light far less. A take whose flashes are not found
   is `flash_not_found`, so the two cameras cannot be combined for metrics (each camera alone still gives its metrics). The
   BUG-0066 fix plan starts with "measure the real lamp in the real scene", and that needs a recording. So a **rehearsal
   without a performer** should come first (Q3).
2. **The agent is a model service: an image or a sound it opens leaves this machine.** TECH_WORKFLOW §10.1 says no video
   goes to an outside service, and consent box (c) says the video stays on the project's machine. So for any file with a
   person in it the agent opens **no frame, no picture, no audio and no raw `ffprobe_json` output** (phone files can carry
   tags such as a GPS location and the device name). Its scripts print counts and numbers only, and a person (the
   maintainer or O) does the visual and listening checks at this machine (Q9). Checked in the code on 2026-11-17:
   `probe_video` reads only the `rotate` tag and the proxy is written with `-map_metadata -1`, so no manifest or proxy carries
   the tags; the copied original keeps them (it must stay unchanged). Two more ways out of the machine are on the phones
   themselves: **location tagging** in the camera app and **automatic cloud backup** of the photo library. Both are turned
   off before any recording (C-10).
3. **The helper must leave the frame, not only the area.** The target is chosen in the first frames of a pass as the largest
   box near the centre (`track/target.py`, P3.04, searching 2 s), and a pose pass covers a segment plus 1 s on each side. The
   helper stands in the area for the start cue, so a helper still in view when the standing reference starts can be chosen
   or make the choice `ambiguous`. Protocol 1.1 should say: after the cue the helper leaves the frame, then the performer
   stands still at least 2 s before the reference counts (to be measured, C-5).
4. **The metrics need four things from the take** (P5.02–P5.07): the standing reference of 3–5 s at the start position
   (`Λ_take` of hip height A, P5.03); a true vertical line in each view (the camera roll, P5.02); the camera role
   (`main_axis`, `side_left`, `side_right`, the values of `--role` in `taiji ingest`) and the form direction, from which a
   segment's view category comes (trunk lean, P5.05); the whole body in the frame (coverage, P4.07).
5. **The hardware inventory is a generated file and starts with two stray lines (BUG-0076, S3, registered 2026-11-17 in this
   analysis).** `tools/env_check.py > hardware_inventory.md` writes rtmlib's `load ...` lines into it, and a rerun would erase
   a hand-written phones section. So the phones go to a hand-written file (Q7) and BUG-0076 is fixed on its own.

### 1.4 Scope

**In scope (proposed split, Q3):**

- **P1.09a — Rehearsal without a performer.** Two phones by protocol 1.0, in the real venue. Only the helper's hands and
  the lamp at the cues (no face in view, nobody speaks), a marker pole moved to the corners of the area to check the framing,
  and the checkerboard scan. Measures: the phone formats (C-1, C-2), the lamp and the claps in the real scene (C-3, input of
  BUG-0066 and BUG-0063), the board (C-6), the framing of the area (C-4a), the copy procedure (C-9), the phone privacy
  settings (C-10), the time of each part (C-11). It needs the phones, the venue and one helper, **not** the consent review.
  The same files serve P2.07 step 2.
- **P1.09b — The trial take with the performer.** One full-form take `S00-P00-T01` (and a spare take if Q6 says so) and a
  board scan, by protocol 1.0 with the values found in P1.09a; copy, hashes, all the checks of §2.4; protocol 1.1; the
  records. It needs P1.06 AC2 recorded by O, the signed form, `P00` registered, and the D08 registry row updated **before**
  recording (AGENTS.md §9.4 item 1, §9.5).

**Out of scope:** ingest, proxy and sync of the files (P2.07), the pose run and the clip table (X.27), segments and metrics
(P5.10), the BUG-0066 fix itself (its own lifecycle, decided on the P1.09a numbers), the BUG-0076 fix (its own small fix),
any change of code under `taiji_ai/src`, more than one performer.

### 2.6 Impact / rollback

No code changes; data stay local under `taiji_ai/data/trial/` and on O's disk. If P1.09a shows a problem (lamp, board,
