## 1. Analysis

**Goal:** a small, browser-playable copy of each recording for the UI (P8) whose frames are the source frames with the same
timestamps, so that a frame chosen in the browser is the same frame the pipeline measures.

**Facts read (2026-11-15):** W1 step 5: `ffmpeg -i source -vf scale=-2:720 -c:v libx264 -crf 23 -g 30 -an proxy.mp4`, the proxy
keeps the source timestamps, mapping proxy ↔ source by PTS, check ≤ 1 frame on sample points. T-IO-10 (frame count and
timestamps equal within 1 frame at 10 points), T-IO-11 (a rotated source: upright proxy, same time map). FFmpeg is a GPL build
called as a separate process (THIRD_PARTY_NOTICES §3).

**Planning experiment (2026-11-15, scratchpad, synthetic clips):** a VFR source (60 frames) and a source with 90° display
rotation, three variants (default, `-fps_mode passthrough`, passthrough with `-copyts`): all kept 60 frames with timestamps
equal to the source (max difference 0.000 ms); the rotated source gave an upright 540×720 proxy with rotation 0. Two findings:
(1) `scale=-2:720` **enlarges** a source smaller than 720 lines (640×480 became 960×720), so the filter must be
`scale=-2:'min(720,ih)'`; (2) the default already kept the timestamps with this FFmpeg, but the explicit
`-fps_mode passthrough` is used so that a change of FFmpeg defaults cannot drop or duplicate frames. Phone files with a
non-zero start time or an edit list were not covered: `-copyts` is decided in step 2 on such a fixture.

**In scope:** `io/proxy.py`: `make_proxy(recording_dir, settings) -> ProxyManifest`; the timestamp check; `proxy.json` written
last; CLI `taiji proxy <recording_id>`; ingest (P2.02) calls it as an optional last step (`--proxy`).

**Out of scope:** serving the proxy over HTTP with Range requests (P8), audio in the proxy (the UI plays video only).

**Design:**

- Command (list of arguments, no shell, timeout): `ffmpeg -i source -map 0:v:0 -vf "scale=-2:'min(720,ih)'" -c:v libx264
  -preset veryfast -crf 23 -g 30 -pix_fmt yuv420p -fps_mode passthrough -an -movflags +faststart proxy.tmp.mp4`, then
  `os.replace` to `proxy.mp4`. FFmpeg's automatic rotation applies the display rotation, so the proxy is upright and carries
  rotation 0; `rotation_applied` in the manifest records the source rotation.
- Container tags (finding of the P2.02 review, 2026-11-16): phone files can carry GPS position, device model and creation
  time in the container. P2.02 stores the source as recorded (read-only; it leaves the machine only with `consent_share`);
  the proxy that the browser shows is made with `-map_metadata -1` so that it carries none. To be tested in this task: the
  proxy of a source with a `location` tag has no tag (`ffprobe`).
- Check: `scan_pts_ticks(proxy)` against `pts.parquet`: equal frame counts, then at 10 evenly spaced frames (first and last
  included) `|t_proxy − t_source| ≤ 1 frame` (median source dt); the maximum over **all** frames is also recorded. `passed =
  false` keeps the proxy but marks it unusable; the UI must then refuse frame-accurate work on it.
- `ProxyManifest` (`proxy/1`) with the FFmpeg version, the arguments, both SHA-256 values and the check.

### 9.2 Analysis (what the probes showed)

- **BUG-0052.** A clip trimmed on a phone is a stream copy that starts between two keyframes, so the file has an edit list.
  Synthetic clip: base 4 s, 30 fps, `-g 15`; `ffmpeg -ss 0.7 -i base.mp4 -c copy trimmed.mp4`. `ffprobe`: 105 packets, six
  with the flag `D` and negative `pts_time` (−0.200 … −0.033); PyAV decode and `ffprobe -count_frames`: **99** frames, the
  first at `pts` 0 = stream `start_time`. `scan_pts_ticks` (`io/frames.py`) keeps every packet with a `pts` and a size, so
  `pts.parquet` has 105 rows, six with negative `t_sec`; row *i* is not decoded frame *i*. `Packet.is_discard` exists in
  PyAV 19.0.2 and removes exactly those six (105 → 99, smallest kept `pts` 0). The real database holds no recording yet
  (0 rows), so nothing needs to be re-ingested.
- **BUG-0055.** `taiji proxy` on a tampered `pts.parquet` prints `check failed`, exits 0, log level INFO. `ingest --proxy`
  with a failing proxy step (ffmpeg not found) prints `error: ...` without the recording ID although the recording was
  stored; the same command run again recovers.
- **BUG-0053.** Mutation run: 23 mutants, 8 caught, 15 survived (one equivalent: `-fps_mode passthrough`).
- **BUG-0054, BUG-0056:** as registered.
