## 1. Analysis

**Goal:** answer with numbers, on the maintainer's machine, three questions that the next tasks and gate G01 depend on:

1. **How fast is the pose stage?** Real-time factor (RTF = processing seconds / video seconds) of `run_pose` per clip and per detector cadence N (1, 5, 10), split into decode, detector, pose and the rest; per-frame latency p50 / p95 / p99; RTF over 1 s windows p50 / p95 (B-PERF-01); the time of the whole pose stage for one 30 s segment.
2. **How much GPU memory?** Peak VRAM of the process per N, above the baseline that other programs already hold, against the 12 GB of the card.
3. **What does N cost in quality?** The detector runs every N frames and boxes in between come from the previous keypoints (P3.02). Measure what N = 5 and N = 10 change against N = 1 (detector on every frame): persons lost or late, keypoint distance (in pixels and in body heights), and what it does downstream (the chosen target, `tracked` share, `target_lost`, `needs_reselect` of P3.04 to P3.06). Then apply a decision rule **written before measuring** and recommend N.

Plan row P3.07: *"Benchmark on 5 real clips (P1.09): RTF, peak VRAM, N = 1/5/10, effect of N on the keypoints"*, deliverable `reports/p3_pose_benchmark.md`, test "real numbers". B-PERF-01 (plan section 15): *RTF (p50/p95), peak VRAM, end-to-end time of one 30 s segment* (P3.07, P11.03). G01: *"RTF/VRAM measurable"*. The plan sets **no target** for any of these numbers.

**In scope:**
- `taiji_ai/src/taiji_ai/bench/` (new package, measurement logic with unit tests): `timing.py` (a timing wrapper of the pose model, latency and window statistics), `compare.py` (match the persons of two runs, distances, entry delay, downstream summary), `gpu.py` (VRAM sampler on NVML), `decision.py` (the written rule for N).
- `run_pose(..., on_frame=None)`: an **additive, optional** callback `on_frame(position, t_sec)` called after each frame; the result does not depend on it (needed here for per-frame latency, and by P7 for progress).
- `tools/bench_pose.py` (CLI: `run` orchestrates, `worker` is the process that measures one N): ingest into a **throwaway data folder**, one fresh process per N, JSON of all numbers into `taiji_ai/data/reports/p3_07/` (ignored by git).
- The report `Docs/reports/p3_pose_benchmark.md` (numbers and analysis only; no frame, no keypoint, no file name, no personal path), README, plan rows, W4 text, `THIRD_PARTY_NOTICES.md` (NVML), DECISIONS, tracking.

**Out of scope:** changing the default `detect_every_n` (the recommendation goes to the maintainer; the change is a separate decision, Q7), YOLO11 (P3.09), failure cases (P3.08), accuracy against labels (PCK needs the 200 audit frames: later), TensorRT, batching, CPU fallback timing, 60 fps and phone files (they do not exist yet), proxy, sync and the other stages, the worker and GPU job lock of P7.

**Inputs / outputs / units:** inputs: four local videos (D20) found by size and SHA-256 (never by file name), the verified model registry. Outputs: JSON (all numbers, per pass), the report. Units: seconds, milliseconds per frame, MiB, pixels of the 1920x1080 image, body heights (the hull height of the reference person, dimensionless). Timing uses `time.perf_counter`; ONNX Runtime calls are synchronous, so the time around `detect` and `estimate` is the time of the GPU work plus pre- and post-processing.

**Facts established while planning (2026-11-16, read-only probes):**

- **Per-process VRAM is not available on this machine:** `nvidia-smi --query-compute-apps` prints `[N/A]` for every process (Windows WDDM). The **device total** is available. NVML loaded through `ctypes` from the system (`nvml.dll` of the driver) answers in 1.5 µs per call (`init`, handle, memory, name, driver, utilisation all return 0). So the sampler needs **no new dependency** and can sample every 20 ms.
- **The GPU is shared with the desktop:** `memory.used` was 1085 MiB, then 1259 MiB minutes later, and the GPU showed 15 to 16 % utilisation with nothing of ours running. So the peak of our process is `peak total - baseline`, with a stated uncertainty of a few hundred MiB, and the timing has noise from other programs (and from any other agent's GPU run: one GPU job at a time, AGENTS.md 5.7).
- **ONNX Runtime keeps its memory arena:** the VRAM does not go down after a run, so a peak measured in a process that ran another N before is the peak of the largest run. Hence **one fresh process per N**.
- `taiji_ai/data/` has the database but **no recording**: ingest of the four videos (1.3 GB copied, SHA-256 checked) is needed; it goes to a throwaway folder (`data/bench/`, ignored by git), not into the project data.
- `ruff` runs on `tools/` as well as `src` and `tests` in the gate; `mypy` only on `src`.

**What has to be decided (the reasoning, worked out while reading):**

1. **Which clips.** P1.09 does not exist (no performer, phones, venue or date; TASK_STATUS), and DEC-0036 allows D20 for "performance" checks and pose development up to P3.06 but lists `benchmark` among the undecided uses. In the registry `benchmark` means **accuracy against labels** (AGENTS.md 9.4); this task measures speed, memory and **self-consistency of the cadence** (N against N = 1, no labels), which is a technical check ("hiệu năng") of `dev-test`. That reading is mine and needs the maintainer's yes (Q1); the report says in its first lines: D20, not P1.09, not product accuracy, rerun on phone clips when they exist.
2. **The five clips are fixed now, before any number is seen** (no choosing by result): 30 s segments (32 s of frames with the 1 s margins), mixed on purpose for codec, frame rate and crowd:

   | Clip | Video | Start [s] | Codec, fps | What is known |
   | ---- | ----- | --------- | ---------- | ------------- |
   | c1 | d20-v2 | 300 | H.264, 24 | one person in every frame (P3.02) |
   | c2 | d20-v2 | 660 | H.264, 24 | up to four people (P3.05) |
   | c3 | d20-v3 | 600 | H.264, 24 | not seen |
   | c4 | d20-v1 | 500 | AV1, 24 | not seen |
   | c5 | d20-v4 | 1200 | AV1, 30 | not seen |

   Frames per pass: 4 x 768 + 960 = 4032. The persons per frame of each clip are measured and reported, not assumed.
3. **RTF and what it contains.** RTF = `elapsed_s` of `run_pose` (decode, model calls, box derivation, bookkeeping) divided by the video span of the frames processed (`t_sec[-1] - t_sec[0] + median dt`, about 32 s). Phase split: **detect** and **estimate** by a wrapper around the model (the runner is not changed for this); **decode** by a separate pass of `iter_frames` over the same window (same rotation, BGR conversion included); **other** is what remains. Because the cost is per frame, the report also gives **ms per frame** and the RTF it implies at 30 and 60 fps (a phone at 60 fps doubles it).
4. **p50 / p95 of B-PERF-01** are taken over **1 s windows of video** pooled over all clips and measured passes (a per-frame wall-clock series comes from `on_frame`); per-frame latency p50 / p95 / p99 is given too. Per-clip RTF is the median of three measured passes with the minimum and maximum next to it.
5. **Warm-up and cold start.** The first pass of each worker is a warm-up (cuDNN algorithm search, arena growth) and is **not** counted in the RTF; it is reported separately with the model load time as the cold start.
6. **Peak VRAM** per N, from the fresh worker: baseline (median of 25 samples over 0.5 s before the models load), after load, peak during the warm-up, peak during the measured passes; the number reported is `peak total - baseline` and the total peak next to the 12288 MiB. The baseline drift (min and max over the 5 s before the load) is reported; a drift above 300 MiB marks the number as uncertain.
7. **The effect of N** is computed from the **first measured pass** of each N on the same frames (the passes are bit-identical in P3.02; the tool checks it and says so): per frame the persons of run N are matched to the persons of N = 1 by Hungarian assignment on the mean keypoint distance over the keypoints valid in both (at least 4 common), normalised by the hull height of the N = 1 person; a pair is accepted when the cost is at most 0.5 body height. Reported per clip and pooled: person-count agreement (share of frames with equal counts), person-frames missed and extra, **entry delay** (frames until a person of N = 1 appears in N), keypoint distance median, p95, p99 and maximum in px and in body heights, the p95 per joint group (head, trunk, arms, legs, feet), and the share of persons that cannot be compared (fewer than 4 common valid keypoints), which are counted, not dropped. Downstream: `select_target`, `associate_tracks`, `resolve_target` on each run: is the target the same person as in N = 1, the share of `tracked`, `lost`, `target_lost` frames, the events, `needs_reselect`.
8. **The decision rule for N, fixed now (provisional, an engineering choice, not a metric threshold, AGENTS.md 5.5):** against N = 1, pooled over the five clips, N is **acceptable** when (a) person-count agreement is at least 99 %; (b) the keypoint distance p95 is at most 0.01 body height and p99 at most 0.03; (c) the `tracked` share of the target is not lower than N = 1's by more than 0.5 percentage points and no clip gets `needs_reselect` that N = 1 does not have. The **recommendation** is the largest acceptable N, except that N = 10 is recommended over N = 5 only if it is at least 15 % faster than N = 5 in median elapsed time (otherwise the shorter, safer cadence). If N = 5 is not acceptable the recommendation is N = 1. The numbers 0.01, 0.03, 99 %, 0.5 points and 15 % come from the P3.02 measurement (p95 5.68 px is about 0.007 of a body height of 800 px; the maximum 47 px about 0.06) and from reading, not from a reference; the rule is written so that the maintainer can change it **before** the measurement. A result that contradicts expectations is reported, the rule is not adjusted after the fact.
9. **Repeats and noise.** One warm-up and three measured passes per clip and N. A (clip, N) cell whose spread (max - min) / median is above 10 % is repeated up to two more times and is marked noisy if it stays above. The GPU utilisation before the run is recorded; nothing else of ours (the gate, other GPU tests) runs during the measurement.
10. **The `on_frame` callback** is the only change of `run_pose`: optional, default `None`, called after each processed frame with `(position, t_sec)` where the position counts frames of the window from 0; an exception in the callback is not caught (it ends the run like any other error, no partial result). The result must be identical with and without it (T-BENCH-05).

**Constraints that apply:** AGENTS.md 5.2 (frames by real PTS: `run_pose` unchanged), 5.5 (no universal thresholds: the rule in point 8 is for choosing a parameter, written as provisional), 5.6 (models only from the registry: the worker builds the estimator from it, no download), 5.7 (one GPU job at a time; heavy work in a subprocess: the tool runs the measurement in a worker, never in the API), 5.9 and 9.4 (D20 stays out of git; no frame or keypoint is stored in the repository; the report holds aggregate numbers only; the clips are named `d20-v1..v4`, never by file name; derived artefacts here are speed and agreement statistics, not a dataset), 9.1 (NVML is the driver's own library, proprietary, installed with the driver, called through `ctypes`, nothing bundled: recorded in `THIRD_PARTY_NOTICES.md`), 6 (type hints on public functions, no `print` in `src` (the tool prints), logs with IDs only).

**Unknowns, risks:**

1. *Other GPU load* (the desktop, another agent's tests) changes both the timing and the VRAM baseline; mitigated by the repeats, the spread rule, the recorded baseline and utilisation, and by saying so in the report. A run that is clearly disturbed is repeated, never edited.
2. *Peak VRAM is the memory the process holds* (arena, cuDNN workspace), not the minimum that would be needed; it is the number that matters for sizing, and the report says what it is.
3. *The "effect of N" is a consistency measure*: N = 1 has its own errors; nothing here says which keypoints are right.
4. *D20 is not the target footage:* a large, mostly static presenter, a fixed camera, AV1 and H.264 at 24 and 30 fps. Phone clips (H.264 or HEVC, 30 fps, other lighting and size) can differ; the tool is made to be rerun on them (proposed follow-up X.27, blocked by P1.09).
5. *Matching persons between runs* can fail where two bodies overlap (the limit of P3.05); such pairs show up as "missed and extra", which makes the agreement figure pessimistic, and the report counts them separately.
6. *Disk:* ingest copies 1.3 GB into the throwaway folder; it is deleted at the end unless `--keep` is given.
7. *Run time:* about 25 minutes of GPU time (N = 1 at about 0.9 s per second of video dominates: 32 s x 5 clips x 4 passes x 0.9 = about 10 minutes; N = 5 about 4 minutes; N = 10 about 3 minutes; decode passes and ingest the rest).

## 2. Plan

**Design:**

`bench/timing.py` (numpy only, no I/O):

- `TimedModel(model, clock=time.perf_counter)`: implements the `PoseModel` protocol (`detect`, `estimate`, `providers`, `model_fingerprint`) by forwarding to the real model and adding the duration of each call to `detect_s` / `estimate_s` and counting `n_detect` / `n_estimate`; exceptions propagate unchanged (the time of a failed call is not added).
- `FrameClock(clock)`: `on_frame(position, t_sec)` appends `clock()`; `latencies()` gives the time between consecutive frame callbacks (the first frame's latency is measured from the `start()` mark), raising `BenchError` if the frame count is zero or the times are not increasing.
- `window_rtf(wall, t_sec, window_s=1.0) -> np.ndarray`: for each 1 s window of video time the wall seconds spent on its frames divided by the video seconds they cover (the last partial window is dropped and counted); `percentiles(values, (50, 95, 99))`.
- `video_span_s(t_sec)`, `rtf(elapsed_s, span_s)`, `fps_equivalent(ms_per_frame, fps)`.

`bench/compare.py`:

- `match_persons(raw_ref, raw_other, frame)` -> pairs, missed, extra, uncomparable (Hungarian on the mean keypoint distance over common valid keypoints, normalised by the reference hull height, gate 0.5 body height, at least 4 common keypoints).
- `compare_runs(raw_ref, raw_other) -> RunComparison` (frozen dataclass): person-count agreement, missed, extra, uncomparable, entry delays, distances in px and in body heights (all pairs pooled: median, p95, p99, max), p95 per joint group (`JOINT_GROUPS`: head, trunk, arms, legs, feet by the HALPE_26 names). Requires the same frames (`frame_index` and `t_sec` equal) or raises `BenchError`.
- `downstream_summary(raw) -> dict`: `select_target`, `associate_tracks`, `resolve_target`: chosen track id and the person's keypoints at the selection frame, shares of `tracked`, `lost`, `target_lost`, number of events by kind, `needs_reselect` and its reason; `same_target(summary_ref, summary_other, raw_ref, raw_other)` compares the chosen person by keypoint distance at the selection frame.

`bench/gpu.py`:

- `Nvml` (loads `nvml.dll` through `ctypes` with an injectable loader for tests; `init`, `device_name`, `driver_version`, `memory_used_mib`, `total_mib`, `utilisation_pct`, `shutdown`); raises `BenchError` with the reason when the library or a call is missing.
- `VramSampler(nvml, interval_s=0.02)`: a thread that samples `memory_used_mib`; `mark(label)` records the label with the current maximum; `baseline()` (median of the samples before the first mark), `peak()`, `drift()`; `stop()` joins the thread; used as a context manager. When NVML is not available the tool writes `vram: {"measured": false, "reason": "..."}`, never a number.

`bench/decision.py`: `recommend_n(stats_by_n, rule=DecisionRule()) -> Recommendation(n, acceptable: dict[int, bool], reasons: dict[int, list[str]], speed_gain_10_vs_5)` implementing point 8; `DecisionRule` is a frozen dataclass of its numbers (validated).

`pose/runner.py`: `run_pose(..., on_frame: Callable[[int, float], None] | None = None)`; the call sits after `offsets.append(...)` and `followed = ...`, inside the loop, with the window position `k` and `frame.t_sec`.

`tools/bench_pose.py`:

- `run --video-dir video --out data/reports/p3_07 [--keep] [--ns 1,5,10] [--repeats 3] [--clips c1,...]`: finds the four videos by size and SHA-256 (table in the tool, from the registry), refuses if one is missing or differs (exit 2, names the label only), ingests them into `data/bench/<run>/` with a test participant, runs one worker process per N (`python tools/bench_pose.py worker ...`), reads the workers' JSON, runs the comparison and the decision rule, writes `bench.json` and `report_tables.md` (the tables of the report, generated, so that no number is typed by hand), prints a short summary (labels and numbers only), deletes the throwaway folder unless `--keep`.
- `worker --recording-dir ... --n N --clips ... --repeats ...`: builds the estimator from the registry (model load time recorded), starts the VRAM sampler, runs the warm-up and the measured passes with the `TimedModel` and the `FrameClock`, a decode-only pass per clip and repeat, the end-to-end of one 30 s segment (run, `associate_tracks`, `select_target`, `resolve_target`, `save_pose_raw`, `save_track` into a temporary file), saves the `PoseRaw` of the first measured pass of each clip to a temporary `.npz` for the comparison (deleted at the end; it holds keypoints of the videos and never leaves the throwaway folder), prints one JSON.
- The tool prints no file name, only `d20-v1..v4` and clip IDs.
