## 1. Analysis

**Goal:** turn "the chosen person" and "the tracks of everybody" into **one person over time**: for every frame the keypoints of the performer, or an honest "not observed" with the reason, never a jump to somebody else. Then write that as `track.parquet`, the single-person input of the quality layer (P4).
W5 step 3: the target is lost when absent for more than `max_lost` (proposed 0.5 s): mark `target_lost`, never jump to another person; when seen again, re-attach **only if the cost is under a threshold**, otherwise tell the user to choose again. W5 step 4: `track.parquet` with `t_sec`, `frame_index`, keypoint, score, `match_cost`, `status`.

**What the plan, workflow and code say (read 2026-11-16):**

- Plan row P3.06, T-TRK-04 (absent longer than `max_lost`: `target_lost`, no jump to another person) and T-TRK-05 (back within the cost threshold: re-attach; outside: ask the user to choose again). SYN-12's tolerance row: `target_lost` interval equals `expected_target_lost(scene, max_lost_s)` within **one frame**
  (`tests/helpers/synth.py`: for each absence longer than `max_lost_s`, from `start + max_lost_s` to the return of the target; with the defaults `((2.0, 2.5),)` for `max_lost_s = 0.5`).
- What P3.05 gives (see its hand-over note): per person row `track_id` (-1 weak), `match_cost`, `match_margin`, `gap_frames`, `gap_s`; per track first and last frame; a track that is not matched lives 0.1 s, so an absence of more than 0.1 s ends the target's track and the returning person has a **new** track; the target's track id is
  `track_of_person(tracks, select_target(raw).person_row)`. `select_target` (P3.04) gives the frame, person row, box, `ambiguous`, `weak`, `offset_from_start_s`.
- P4 (plan section 8) needs one array of keypoints and scores per frame (NaN where the person was not observed), the real `t_sec`, and the reason a frame is empty. Keypoints are **never** filled or interpolated here: P4 interpolates short gaps (<= 150 ms) by time and keeps long gaps NaN.
- Conventions: Pydantic models with `schema_version` in every persisted file; atomic writes; NaN = not observed; no paths or file names inside artifacts; `pts.parquet` already stores a schema-metadata JSON (`time_base`, `start_pts`), `store/artifacts.atomic_write_parquet` keeps schema metadata; the P3.03 reader and writer (`pose/raw_io.py`) are the model for strict, versioned, atomic persistence.

**What has to be decided (the reasoning, worked out while reading):**

1. *Who may be re-attached.* The distractor in SYN-12 stands in the frame during the absence and has a track that began **before** the loss: it must never be a candidate. Only a track that **starts after the target's last frame** can be the returning performer. That already rules out "jumping" to anybody who was there.
2. *What "cost under a threshold" compares.* The first pose of the new track against the **last pose of the target** with the cost of P3.05 (`1 - IoU` of hulls and keypoint distance over height, in [0, 1]); the function is private in `associate.py` and is made public here. After a long absence the position can differ, so the threshold decides; the real
   values are measured first (step 2) on SYN-12 with `return_offset_px` from 0 to 300 and on **real clips with a simulated absence** (the presenter's persons removed for 0.3, 1 and 3 s from the five saved clips of D20, so the cost of a true return is a real one).
3. *Two candidates at once.* A bystander entering near the place where the performer vanished can pass the threshold as well. If two new tracks start in the same frame and both are under the threshold, the choice is **ambiguous** when their costs are close: `best cost / second cost >= ambiguity_ratio` (0.6; both costs 0 also counts as close). Then there is no re-attachment and the user is asked. Never a guess.
4. *Statuses.* Per frame: `tracked` (the target's keypoints are there), `lost` (the target is missing for at most `max_lost_s`: expected to come back), `target_lost` (missing for more than `max_lost_s`; the user may need to choose again), `before_target` (before the first frame in which the target exists, for example a performer who enters after the margin starts).
   In `lost` and `target_lost` frames the keypoints and scores are NaN. The boundary between `lost` and `target_lost` is `t_sec - t_last_seen > max_lost_s` with the real times, so it falls within one frame of `expected_target_lost`.
5. *`needs_reselect`.* The file carries a flag: true when the target is `target_lost` at the last frame, or a re-attachment was refused (over the threshold or ambiguous) and never succeeded, or the default choice of P3.04 was `ambiguous`. The UI (P8) shows it; this task only sets it and says why (`reselect_reason`).
6. *Rows.* One row per frame of the `PoseRaw` (including the 1 s margins), with `in_segment` telling which are inside the segment; P4 needs the margins for the filter. Tracks of P3.05 run over all frames, so the performer's history before the selection frame comes from the same track.
7. *The weak target.* If the person chosen by the user is weak (`track_id = -1`) the target cannot be followed: a clear error, not a silent file full of `target_lost`.

**In scope:** `track/state.py`: `resolve_target(raw, tracks, selection, *, params=None) -> TargetTrack`, `TargetStateParams`, `TargetTrack`, `TargetStateError`; `person_cost` made public in `track/associate.py`; `schemas/track.py`: `TrackMeta` (schema `track/1`); `track/track_io.py`: `save_track`, `load_track`, `TrackFileError`; tests; README, plan rows, W5 text, tracking.
**Out of scope:** interpolating or filling keypoints (P4); deciding the performer (P3.04) or the associations (P3.05); where the file lives and its name (P7: `runs/<run_id>/track.parquet`) and the run manifest checksum (P7); the UI that asks the user to choose again (P8); smoothing.

9.4 point 7 (no dataset content in the repository).

**Unknowns, risks:**

1. *The re-attachment threshold decides between "the performer came back" and "ask the user"*: a value that is too high attaches a stranger who happens to arrive at the same place, one too low asks the user for every return. It is measured (step 2) on synthetic returns and on real clips with a simulated absence; there is **no real clip with a real absence yet** (P1.09), so the number is provisional and is re-measured on the first real takes.
2. *Two identical-looking people at the same place* (the limit written in P3.05): a re-attachment after such a crossing can be wrong without any signal except `match_margin` near 0 before the loss; `reselect_reason` says when the last match was contested.
3. *A performer who stands still while another person walks through* is handled by P3.05; this task only sees tracks.
4. *The performer at the edge of the frame* leaves and returns often: many short `lost` runs; the counts in the metadata make that visible to the UI and to P4.
5. *Large files*: 6 minutes at 30 fps is about 10 800 rows of 52 + 26 floats: a few MB.

## 2. Plan

**Design:** `track/state.py` (about 200 lines, numpy only, no I/O). `TargetStateParams` (frozen, validated): `max_lost_s = 0.5`, `reattach_cost` (from step 2), `max_reattach_s = 5.0`, `ambiguity_ratio = 0.6`. The loop over frames keeps the current target track and the pose and time of the last frame in which the target was seen:

1. frames before the first frame of the target's track: `before_target`;
2. a frame in which the current track has a person: `tracked` (copy keypoints and scores of that person row, its `match_cost` and `match_margin`);
3. otherwise the target is missing: `lost` while `t - t_last <= max_lost_s + eps`, `target_lost` after; keypoints NaN;
4. when a track **starts** in this frame (its first person) and the target is missing, evaluate the candidates of this frame: cost of each first pose against the last target pose (`person_cost`); keep those at or under `reattach_cost` and within `max_reattach_s` of `t_last`; exactly one: re-attach (the frame is `tracked` from this frame, `reattach_cost` set, event recorded); two or more under the threshold with close costs
   (`best / second >= ambiguity_ratio`): refuse, event `ambiguous`, status unchanged; none: event `refused` once per candidate (over the threshold), status unchanged;
5. at the end: `needs_reselect` as in the analysis (point 5) with `reselect_reason`.

`save_track(path, target_track) -> str` builds the Arrow table and the metadata, validates with `TrackMeta`, writes atomically and returns the SHA-256; `load_track(path)` reads, validates strictly and rebuilds the `TargetTrack` (versions through `_READERS`).

## 4. Implementation log

**Step 2 — measurement before fixing the parameters (2026-11-16; scratch scripts, not in the repository).** The cost of P3.05 (`person_cost`, now public) between the **last pose of the target** and **the first pose after the return**, and between that last pose and other people:

| SYN-12, 50 px | 0.230 to 0.255 | same |
| SYN-12, 100 px | 0.420 to 0.442 | same |

| SYN-12, 200 px | 0.651 to 0.654 | same |

Reading: a return to the same place costs up to about 0.45 on SYN-12 (offset up to 100 px) and 0.5 or less in 83 to 100 % of the real positions; every stranger of the clips costs 0.65 or more. **`reattach_cost = 0.5`**: all measured strangers are refused with a margin of 0.15, a true return above it is refused too and the user is asked (the cheap error; the expensive one is giving the frames to a stranger). On SYN-12 it accepts offsets up to 100 px and refuses 150 px and more (0.56 and up). **Limits of this evidence, stated plainly:** the "true returns" are the presenter's own poses with rows removed (he stayed in the picture, so this is the cost of a return to the same place after a real movement, not of a walk out of the frame and back); the "strangers" are the people of one video, mostly far away, so a stranger who stands exactly where the performer stood is not covered and would cost like a true return (the identical-body limit of P3.05; two such strangers at once are caught by the ambiguity rule). There is no real clip with a real absence yet (P1.09): the number is provisional and is re-measured on the first real takes.
**`max_reattach_s = 5.0`** is **not** fixed by these numbers (the cost hardly depends on the absence length in this data: 98 % at 1 s, 83 % at 5 s, 89 % at 7 s); it is a safety limit: the longer a performer is away the more likely a new person is somebody else, so after 5 s the user decides. Findings of the read-back, none a defect in the delivered behaviour:

1. **Events are advisory.** On load the `reattached` events are compared with the rows (frame, cost, tracked status) and every event is checked for range and time, but `lost`, `target_lost`, `recovered`, `refused` and `ambiguous` are not compared with the status of their frame. The rows and the counts are the authority for P4; a hand-edited file could carry a misleading event. Not registered as a bug (the file is written only by `save_track`, which is built from `resolve_target`); written here so that a reader of the file knows. A later task can add the cross-check if the UI starts to depend on the events alone.
2. **The first version of the plan said `reselect_reason`** and the code gives one reason by precedence (`reattach_ambiguous`, `reattach_refused`, `target_lost_at_end`, `default_choice_ambiguous`); when two apply, the events still say the rest. Decided and recorded in DEC-0037.
3. **Evidence limit, stated again:** all real-clip evidence is a **simulated** absence (rows removed from poses of a presenter who stayed in the picture) and strangers are the other people of one video, mostly far away. A stranger standing exactly where the performer stood costs like a true return; the only protection is two candidates at once (`ambiguous`). `reattach_cost` and `max_reattach_s` must be measured again on the first real take with a real exit and return (P1.09 has none).
4. The mypy gate found four type errors in the first full run (a loop variable reused with a different type in `state.py` and `track_io.py`); fixed by renaming, the behaviour did not change (the 245 tests of the time passed before and after).
